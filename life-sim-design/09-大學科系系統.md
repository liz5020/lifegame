## 9.4 修業年限與畢業年齡

| 科系分類 | 修業年限 | 標準畢業年齡(不含延畢) |
|---|---|---|
| 醫學系、牙醫學系、獸醫學系 | 5年 | 23歲 |
| 其餘7大類 | 4年 | 22歲 |

- 【定案】延畢規則:畢業年齡 = 科系標準修業年限對應年齡 + 延畢年數,封頂兩年。觸發原因接既有機制(3.2.4課業與興趣路徑連動、財務壓力等),不另設新判定公式
- 醫/牙/獸科系最晚25歲畢業,其餘科系最晚24歲畢業
- 【定案,9/16 ChatGPT開發審閱發現邏輯衝突+使用者確認採用建議解法】**轉系最後可行年齡**:轉系進醫/牙/獸一律重新起算5年(9.5.1)、其餘科系重新起算4年,若不設上限,20-21歲才轉系會推到超過25/24歲的畢業年齡上限,兩條規則互相矛盾。修正為:轉系當下必須滿足「轉系當下年齡+目標科系修業年限 ≤ 該科系畢業年齡上限(醫牙獸25歲/其餘24歲)」,超過上限時轉系選項不成立(玩家看不到這個選項,或選項顯示但選了會被系統擋下並說明原因)。算出來醫牙獸與其餘科系的最後可行轉系年齡剛好都是20歲(25-5=20、24-4=20)
- 【待驗證】上述年齡上限計算沒有把「已使用的delay_years」一併算入(即轉系當下如果角色已經延畢過,可用的緩衝更少),實作時`isTransferFeasible()`應該把角色目前已用的delay_years also納入計算,而非只看目標科系的基礎修業年限,下一輪實作時一併確認

## 9.5 三個動態狀態機(共通四步驟模板,呼應8.1興趣系統被動/主動雙軌邏輯)

- 【定案】共通流程:① AI於日常回合鋪陳候選情境 → ② 程式判定候選是否成立(兩層骰大方向層) → ③ 呈現明確選項讓玩家決定(AI不能替玩家做最終決定) → ④ 玩家選擇後,兩層骰判定具體結果,細節層由AI發揮

### 9.5.1 轉系

- 候選觸發:連續兩次段考成績低於預期區間【測試參數,見9.7測試項目2】。「預期區間」須是程式可計算的基準(不可由AI自由解讀),log須同時輸出預期區間、實際成績、連續計數、候選判定結果
- 候選成立機率:由才識數值與自律程度決定
- 玩家選項:維持現狀／申請轉系／先觀望不做決定
- 結果判定:複用2.4考試成績算法(才識+備考次數決定落點),不另設新公式
- 【定案】轉系進醫/牙/獸三系,一律重新起算5年,不做學分抵免判斷;轉系須先通過9.4的「轉系最後可行年齡」門檻檢查才成立候選
- 轉系成功後,科系分類、修業年限、預計畢業年齡須同步重算(見9.8欄位規格)
- 【新增,實作建議】需要轉系候選冷卻機制,避免候選連續回合重複出現同一提案,具體冷卻回合數待測試組校準

### 9.5.2 雙主修

- 候選觸發:才識數值達門檻【測試參數,見9.7測試項目3】,或特定科系伏筆權重被觸發
- 玩家選項:申請雙主修／僅維持單一主修
- 進行中:維持既有回合預算,同一批回合敘事同時帶出雙重課業壓力,不新增回合
- 【定案,9/16 ChatGPT開發審閱發現規則缺口+Claude Code依9.1「不新增回合預算」原則判斷,可覆寫】雙主修**完全不影響畢業年齡**,不計入delay_years,只影響課業壓力(敘事層)與財務支出(學費),時間成本zero-cost——理由:若改為計入delay_years,會讓「不新增回合預算」的範圍從原本只有醫牙獸/延畢玩家,擴大到所有選擇雙主修的玩家,跟9.1定調的「局部性影響」原則衝突。**這是Claude Code的判斷,不是內容組正式拍板,如果內容組有不同意見,之後可以推翻改用「雙主修需額外時間、計入delay_years」的另一方案**
- 結果只有兩種狀態,只能結算一次,不重複:完成(`dual_major_status=completed`)、中途放棄(`abandoned`),沿用十四、14.3.2現有「雙主修中途放棄」內容範例
- 【定案,9/16補充,標記測試參數】中途放棄候選觸發:`dual_major_status=active`期間,自律或財務健康度**連續3回合低於40分**(呼應3.7.3的50分中性基準,取中性偏下作為壓力訊號)成立候選;冷卻4回合,避免連續跳出同一提案
- 【定案,9/16補充】候選成立後玩家選項:**撐下去(維持雙主修)／正式撤銷雙主修申請**;撤銷後`dual_major_status=abandoned`,為終局狀態,不可重新申請雙主修(呼應本節「只能結算一次,不重複」)
- 【定案,9/16補充】程式只負責候選成立與狀態轉換,不判斷「應不應該放棄」(呼應9.9責任邊界表既有定案);敘事沿用十四、14.3.2「續補:雙主修中途放棄」現有範例
- 【定案,9/16補充】撤銷後已繳的雙主修學分費不退費——呼應本章第4項(見3.4.4/9.9)學費系統已整體改為家長支付、程式不扣款,此問題連帶不需要處理

### 9.5.3 休學/肄業

- 候選觸發:財務健康度或健康數值低於門檻【測試參數,參照3.4.5醫療費用分級20/50/75分級距概念起草,見9.7測試項目4】
- 【定案,9/16 ChatGPT開發審閱補強】候選觸發條件是**持續低值**,不是單次瞬間跌破——需連續N回合財務健康度或健康數值低於門檻才成立候選,避免單一噪聲事件就觸發休學,呼應3.7.2「持續投入才能累積效果」的既有設計精神,具體N值待測試組校準
- 候選成立機率:由財務健康度與健康數值決定
- 玩家選項:休學一學期(可回到正常就讀狀態)／正式肄業
- 肄業後續:跳轉至肄業當下年齡對應的22歲以後曲線起點,呼應七、7.2職涯不設終身鎖死,肄業不代表人生卡死;`student_status`轉為`withdrawn`後不可再被下學期事件當成在學學生
- 【定案,2026-09-22新增,撤銷本節原本的【待確認】標記】肄業後不可重新入學。理由:9.4的畢業年齡上限(一般24歲、醫牙獸25歲)已讓絕大多數重新入學情境無法成立(例如20歲肄業、22歲想回去讀,22+4就超過上限);開放重新入學需要讓引擎從career模式倒回college模式,還會牽動2.2.1的378回合預算,成本與收益不成比例
- 【本版不做,2026-09-22新增】成年後回學校(在職專班、研究所)日後以十二、職涯章節的「進修」事件處理,不回到學生主狀態
- 【定案,9/16補充,取代原本「不真的暫停回合引擎」的簡化實作】休學須**真正暫停學期引擎**,不只是換敘事包裝:
  - 休學若發生在某學期已消耗部分回合的狀態下,該學期視為**未完成**,不計入已修學分/學期數——復學後從該學期的「開學初」段落重新跑一次,不從中斷點續接
  - 休學期間不套用2.2的27回合完整學期結構(不出現任何考試/課業選項),改用獨立的「休學學期」段落,回合數為7回合【測試參數,2026-09-22修正,取代原本「比照2.3假期段落份量6-8回合」的寫法】——2.3已修正為固定8回合,休學學期是獨立的測試參數、跟代碼既有的`LEAVE_OF_ABSENCE_TURNS=7`一致,不再引用2.3的區間,內容走生活/打工/家庭/自我探索敘事
  - 休學期間:`leave_status=on_leave`,`student_status`維持`enrolled`不轉為`withdrawn`(休學可復學,呼應本節既有定案);`delay_years+=0.5`(呼應9.8既有欄位規格)
  - 復學時:`leave_status`轉回正常,`semester`/`program_year`維持休學前數值不變(不前進);若休學發生在準備期中途,`study_count_this_term`歸零重算,避免復學後沿用過期的讀書次數影響成績落點
- 【定案,2026-09-22取代原本9/16版本】休學選項的可用條件改為兩項都要成立:①`delay_years`尚未達2年上限;②「加上這次休學半年後的預計畢業年齡」不得超過該科系畢業年齡上限(醫牙獸25歲/其餘24歲)——原本9/16版本「`delay_years`封頂兩年已自然限制最多4次休學,不用疊加第二層上限」沒考慮到轉系後起始年齡已提高的情境,轉系後仍可能無限休學到超過畢業年齡上限,詳見9.8.1修正說明

## 9.7 明確待測試項目(交付QA測試部)

1. **轉系候選觸發門檻**:目前草案為「連續兩次段考成績低於預期區間」,請實測校準具體次數與機率門檻,過於頻繁或過於稀少皆須回報
2. **雙主修候選觸發門檻**:目前未定具體才識分數,請依實測數據抓出合理起點分數
3. **休學/肄業候選觸發門檻**:目前草案參照3.4.5醫療費用分級20/50/75分級距概念,請實測校準財務健康度與健康數值各自門檻值是否合適,並確認兩者是否該用同一組級距或分開設計
4. **下游伏筆權重表高/中/低的具體百分比**:請協助抓出各自對應的實際機率區間草案,並實測是否出現某條伏筆線幾乎不會觸發或觸發過於頻繁的失衡狀況
5. **延畢觸發原因與3.2.4課業興趣連動機制的實際掛勾效果**:請驗證興趣拖累課業導致延畢候選觸發的頻率是否合理,避免延畢過於容易或幾乎不會發生

| program_year | 大一~大四／大五 | 轉系重算後正確重置 |
| semester | 上／下學期 | 轉系、休學後不可錯位 |
| delay_years | 累積延畢年數,最小粒度0.5年(對應休一學期) | 封頂2年;休學／雙主修若計入延畢,須跟延畢用同一個欄位累加,不可各自獨立上限(9.5.2已定案雙主修不計入) |
| expected_graduation_age | 預計畢業年齡 | 轉系後即時重算,不能突破科系上限(見9.4轉系最後可行年齡) |
| transfer_cooldown | 轉系事件冷卻 | 避免候選連續回合重複出現 |
| dual_major_status | 無／候選／進行中／放棄／完成 | 狀態一次轉換,不重複觸發 |
| leave_status | 正常／休學 | 休學可復學;肄業不可復學(對應student_status=withdrawn) |
| foreshadow_weights | 科系對5條下游線的權重 | 只影響機率,不做職業鎖定 |

- 【定案】判斷是否已出社會,用`student_status`是否轉為`graduated`/`withdrawn`,不是單純看年齡是否超過22或23歲,避免同一角色同時出現「還是學生」跟「已出社會」的雙重身份判定錯誤
### 9.8.1 delay_years與學期時間軸的對應(2026-09-22新增,取代本節原本的【待補充,實作時決定】標記)

**問題背景**(說明用,非規則):9/16版只定義了`delay_years`這個帳本欄位,沒有規定它跟`timeState.yearInStage`(整數年)怎麼疊加,實作後發現有bug——`collegeTotalYearsRequired()`直接把`delay_years`加進畢業門檻,但`yearInStage`是整數,導致休學1次時畢業時間完全沒有延後、休學2次時延畢時間被「學期重跑一次」與「畢業門檻再多一年」重複計算兩次,且休學期間角色年齡不會前進。

- 【定案】延畢的時間延長一律由「該學期不計入、重跑一次」自然產生,`delay_years`只作為帳本(計數、上限檢查、預計畢業年齡計算),不再加進畢業門檻——畢業判定改為`yearInStage > 科系基礎修業年限(4或5)`,不疊加delay
- 【定案】`computeExpectedGraduationAge()`、`isTransferFeasible()`等「預估/資格檢查」用途仍使用「基礎年限+delay_years」計算,這兩者跟上面的畢業判定用途不同,不衝突
- 【定案】新增半年進位欄位`halfYearCarry`:每完成一次休學復學記半年,累積到2次(滿一年)時角色年齡+1(同步呼叫既有的角色年齡推進機制),欄位歸零
- 【定案】`halfYearCarry`為1時,寒假／暑假標籤對調(休學奇數次後行事曆錯開半年)
- 【定案】帶著`halfYearCarry=1`畢業或肄業、進入22歲以後的職涯曲線時,當年度的回合預算設為對應該年齡帶的一半(下一個生日在半年後),`halfYearCarry`歸零
- 【定案】休學選項的可用條件改為兩項都要成立(取代9.5.3原本「delay_years封頂兩年已自然限制最多4次」的舊定案,見9.5.3同步修正):①`delay_years`尚未達2年上限;②「加上這次休學半年後的預計畢業年齡」不得超過該科系畢業年齡上限(醫牙獸25歲/其餘24歲)
- 【定案】年級標籤(對應`collegeYearLabel()`)不再使用「延畢第N年」這種獨立序數,改為在年級後附註已延畢年數,例如「大四・已延畢0.5年」
- 【定案】日後非休學型的延畢(例如3.2.4興趣拖累成績導致的延畢)一律沿用同一套機制:判定該學期不計入、重跑,`delay_years+0.5`,不另寫第二套機制
- 驗證方式(實作時):4年制科系分別休學0/1/2/3/4次,畢業年齡應依序為22/22.5/23/23.5/24歲(半年以`halfYearCarry`呈現,不重複計算);轉系後休學到上限時,休學選項應正確停用(對應QA手冊U-03/U-04/U-05)
- 影響:**會新增遊戲狀態欄位(`halfYearCarry`)**,實作時需一併評估舊存檔相容性,建議新欄位缺省值視為0,不影響尚未使用休學機制的舊存檔角色

## 9.9 AI/程式責任邊界(開發實作參考,9/16 ChatGPT開發審閱補充,呼應1.2.6兩層骰與8.1興趣系統精神)

| 項目 | 程式負責 | AI可以做 | AI不可以做 |
|---|---|---|---|
| 轉系 | 候選是否成立、成功／失敗 | 描述猶豫、結果與細節 | 自行決定「應該能轉成功」 |
| 雙主修 | 是否申請、進行中、放棄、完成 | 描寫雙重課業壓力 | 自行創造是否完成 |
| 休學／肄業 | 候選、玩家選擇、狀態轉換 | 描寫當下處境 | 自己宣判已休學／肄業 |
| 修業年限 | 標準年限、延畢、預計畢業年齡 | 自然提及距離畢業還有多久 | 自行跳年、改年級 |
| 學費 | ~~金額與扣款~~(9/16改版:學費統一由家長支付,程式不需計算/扣款,見3.4.4) | 純背景細節描寫(例如「學費爸媽已經匯過去了」) | 自行算出金額、透過one_time_transaction/expense_change回報任何學費相關支出 |
| 科系權重 | 伏筆觸發機率 | 描述觸發內容 | 因敘事看起來合理就強制觸發 |

- 【新增,實作建議】建議大學科系系統實作順序:①先建立9.8的學生主狀態模型(科系/修業年限/學年/學期/延畢/預計畢業年齡/學生狀態) → ②接上既有考試/才識/財務機制,不新增第二套學業公式 → ③實作轉系/雙主修/休學/肄業四個狀態機 → ④最後才做8大科系下游伏筆權重校準與內容擴充 → ⑤全部穩定後才跑批次人生測試檢查總回合數,不因單一事件測試結果就直接修改全局回合預算(呼應2.5.2已結案的1234~1404回合目標)
