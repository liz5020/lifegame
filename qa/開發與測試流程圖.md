### 迴圈2 真正的原因（查證結果）

你的猜測**對一半**。

**依據1：版本號通常不是在全套之後才換。** 最近的功能提交，版本號、更新說明、DEPLOY.md 那一行，都和程式放在同一個提交裡：
- `30f000c`（候補當天補位）同時改了 `index.html`、`DEPLOY.md`、`worker/worker.js`。
- `a7eecbc`、`8ae2ce6`、`e69941b`、`9158671` 也一樣。

所以「每次都是全套過了才換版本號」不是常態。

**依據2：真正讓內容在測過之後又變動的，是下面三種情況。**

1. **合併分支時把更新說明併成同一版**：
   - `010e045`（合併 waitlist-fill）在合併提交裡改了 `index.html` 的 `RELEASE_NOTES`（標題從「雲端存檔小調整」改成「候補更快輪到」，多一條說明），也改了 `DEPLOY.md`。
   - `d6e921b`（合併 master，版本合成 2026.10.10-e）也改了 `index.html`、`worker/worker.js`、`DEPLOY.md`。
   - 合併前各分支測過的內容，和合併後要推的內容不一樣。
2. **推之前的小修改**：`17e7cca` 在合併之後又改了 `worker/dashboard.js`（版面微調）。
3. **被測試讀到的「文件」也算輸入**：
   - `tests/test-54-version.mjs` 讀 `index.html`、`worker/worker.js`、`DEPLOY.md`。檢查 `APP_VERSION`／`WORKER_VERSION` 的格式、兩者一致、`DEPLOY.md` 有這個版本號、`RELEASE_NOTES` 第一筆對得上版本號。
   - `test-90-regen.mjs` 還讀 `CLAUDE.md`。
   - 改 DEPLOY.md 或 CLAUDE.md 看起來是「只改文件」，其實會改變測試結果。

**依據3：規則有兩個檢查點，卻沒有辦法證明「這份內容已經測過」。**
- `CLAUDE.md`「commit前一定跑全套」，`WORKFLOW.md` 第4節步驟7「全套全部通過後我也直接推」。
- commit 和 push 之間只要動過任何一個字，就只能整套重跑來證明。
- 紀錄裡看不出每次到底跑了幾次全套（CHANGELOG 只寫結果），**這一點不確定**。但上面三種情況都一定會引發重跑。

**結論**：迴圈2的主因是「測過之後內容又變了，而且沒有工具判斷變的地方會不會影響測試」，不只是版本號的順序。圖B、圖C的解法是：上線前要改的東西全部改完才跑那一次全套，之後用 `--verify` 證明內容沒變。

## 圖B：建議的流程（2026-10-10 規則改寫後）

```
 改程式
   ↓
 ① 只跑這次碰到的那一支 ……………………… 幾秒
      node run-all.mjs 84
   ↓
 ② 跑相關幾支 ……………………………………………… 十幾秒到一分鐘
      node run-all.mjs 84 90 41
   ↓
 ③ --quick（略過兩個長程模擬）…………… 實測見下方「慢的來源」
      失敗 → 先分類：
        程式真的壞了 → 修 → node run-all.mjs --failed 只補跑失敗的那幾支
        測試太脆（寫死文字、版本號、數字）→ 不用重跑蓋過，
          記進失敗歷史（--history），之後改成檢查行為
   ↓
 ④ commit（不換版本號）── 回到「改程式」做下一件事
      ……一組事情做完、使用者決定要發佈時，才往下……
   ↓
 ⑤ 上線前要改的東西「全部」改好（最後一步統一改一次）
      APP_VERSION、RELEASE_NOTES（累積的改動合成一則）、WORKER_VERSION
      CHANGELOG.md、DEPLOY.md 那一行
      合併分支、版面微調，都在這一步之前做完
   ↓
 ⑥ 全套「唯一一次」 node run-all.mjs ……… 約 5 分鐘
      全部通過 → 寫下通過戳記 tests/.last-pass
      有失敗 → 分類 → 修 → --failed 補跑 → 最後仍只再跑一次全套
      跑完之後不再改任何檔案
   ↓
 ⑦ node run-all.mjs --verify ………………………… 1 秒以內
      一樣 → 「這份內容已經全套通過，免重跑」→ 可以推
      不一樣 → 列出哪些檔變了 → 回到 ⑥（正常現象，不能略過）
   ↓
 推（見圖C）
```

```
 快速通道：急著上線的純文字修正（RELEASE_NOTES、說明頁文字等）
   → node run-all.mjs 54 加 --quick
     （--quick 已含其他會讀到這些文字的 test-38、test-80；
       兩個長程模擬不讀這些文字）

   ‧index.html 的遊戲邏輯、worker/ 底下任何檔、tests/ 底下任何檔
   ‧lunar.min.js、og.png、build-pages.sh
   ‧被測試逐字比對的檔：
       life-sim-design/10-存檔與帳號系統.md（test-80 比對說明頁全文）
       life-sim-design/16-介面與視覺設計.md（test-81 比對試看花絮）

```

## 圖C：改完到上線（一次「發佈」）

```
 平常：改 → 單支／--quick → commit（不換版本號、不推）……重複
   ↓
 ① 使用者決定發佈時間（一天 2～3 次，測試參數；Claude Code 問，不自己訂）
   ↓
 ② 最後一步統一改完
      index.html：APP_VERSION、RELEASE_NOTES 最前面加「一則」
                  （把這次累積的改動合成玩家看得懂的說明；防暴雷）
      worker/ 有改：WORKER_VERSION 換成同一個編號
      CHANGELOG.md
      DEPLOY.md：一個版本一行，註明含幾個 commit
      → node run-all.mjs 54 先確認版本檢查通過（幾秒）
   ↓
 ③ 全套「唯一一次」 node run-all.mjs → 全過才寫戳記
   ↓
 ④ commit
   ↓
 ⑤ node run-all.mjs --verify → 印「免重跑」才往下
      （--verify 做好之前的過渡：使用者明確說「已跑過全套、之後沒改」時，
        用 git status 與目前提交確認沒有未提交的改動，就直接推）
   ↓
 ⑥ 推上 master（push）  git push origin HEAD:master
      仍要先問：測試有未通過／未測試、遊戲狀態結構變動、動到 worker 部署設定
   ↓
 ⑦ 等 1～2 分鐘，用 gh 查建置（Workers Builds 與 Cloudflare Pages 都 success；
     Worker 比較慢，in_progress 就再等）
   ↓
 ⑧ 查線上版本：網頁 APP_VERSION、Worker /version 都等於這次的版本號
   ↓
 ⑨ 回報「已上線」→ DEPLOY.md 同一行補「已上線」與提交代號（純文件，--quick 後推）

 緊急件（玩家玩不下去、會花錢的錯誤，或使用者說「馬上上線」）：
   從線上 master 開乾淨分支 → 只放這個功能的 commit → ②～⑨
   → 發完把線上新版本合回原本的工作線，回報有沒有衝突
   拆不開 → 先告訴使用者；先推後測只在使用者明確要求時
```

### 三份文件說法對不上的地方

2026-10-10 第三部分已依新規則改寫共同基準、`WORKFLOW.md` 第4節、`CLAUDE.md`、`DEPLOY.md`，原本的落差處理如下：

1. **上線前跑哪種測試**：
   - 原本 `DEPLOY.md` 只寫跑 `54`，`WORKFLOW.md`／`CLAUDE.md` 寫全套。
   - **已統一**：先跑 `54` 確認，再跑唯一一次全套，推之前 `--verify`。
2. **DEPLOY.md 那一行什麼時候加**：
   - 原本 `DEPLOY.md` 寫上傳後加、`CLAUDE.md` 寫使用者說上傳了才補，但 test-54 要求上線前就要有。
   - **已統一**：發佈前加一行，上線後在同一行補「已上線」與提交代號。
3. **全套耗時**：`CLAUDE.md` 原本寫 4.5 分鐘／45 秒（4 支同時）。**已更新**為這台 8GB 電腦的實測。
4. **推完怎麼確認**：
   - `WORKFLOW.md` 只寫查線上版本，`DEPLOY.md` 還要求用 `gh` 查建置。
   - 這次沒改（新規則沒寫到）。**仍不一致**，建議 WORKFLOW 補一句「見 DEPLOY.md 用 gh 查建置」。
5. **能不能自己推**：
   - 新規則第5條「發佈時間點由使用者決定」，和使用者先前交代的「沒聽到確認上線不推 master」一致。
   - 純文件「--quick 通過即可推」和第5條的關係：2026-10-10 使用者決定純文件隨時可推，已寫進共同基準。

## 慢的來源（2026-10-10 實測）

- 跑法：`cd tests && node run-all.mjs`，不加選項，提交 `8a9f389`（2026.10.10-h 加兩筆後台修正），這台電腦 8GB 記憶體（同時 2 支）。14:47:18～14:52:23，期間沒有其他工作階段改動資料夾。
